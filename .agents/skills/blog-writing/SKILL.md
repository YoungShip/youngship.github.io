# YoungShip 博客写作

## 定位与授权

- 目标仓库：`https://github.com/YoungShip/youngship.github.io.git`；网站：`https://youngship.github.io/`。
- 本技能随仓库位于 `.agents/skills/blog-writing/`。以包含它的仓库为目标，先用 `git rev-parse --show-toplevel` 核对根目录及 remote 是否匹配；不得依赖某台电脑的固定路径。若被单独安装，使用用户指定的检出，无法确认则先询问，不在无关仓库落稿。
- 多台电脑协作时，开始写作前检查远端更新；工作区干净且只需快进时可同步。若有未提交内容、分叉或冲突，保留现场并说明，不自动 stash、覆盖或强推。`.local-drafts/` 不随 Git 同步，不能承诺另一台电脑能恢复未发布草稿。
- 先读目标仓库适用的 `AGENTS.md`，再检查工作区改动、`_config.yml`、`admin/config.yml` 和一篇现有文章，以当前文件为准。
- Skill 不授予 GitHub 权限。使用环境已配置的 Git/连接器认证；不提取浏览器令牌、打印凭据或把密钥写进文章、仓库、Skill。若没有认证，只完成草稿并说明缺少的授权，不申请所有仓库权限。

## 写稿模式（默认）

- “写一篇”“整理一下”“改稿”只授权创作，不授权提交或推送。“保存草稿”也不是公开发布。
- 根据用户素材写作，保留其口吻；不编造亲历、测试结果、数字、引语或参考来源。将推测与已知事实区分开，必要的缺失信息留作待确认，不替用户断言。
- 默认中文；结构随内容决定，不把每篇随想都写成固定技术报告。踩坑记录可按现象、环境、排查、原因、解决、验证组织；只有素材支持时才填相应细节。
- 默认在检出目录的 `.local-drafts/` 写 Markdown 草稿。先用 `git check-ignore` 确认目标会被忽略；若该目录已被跟踪或不被忽略，改用用户指定的仓库外本地目录，或直接在聊天中交稿。不要把未审核稿放入 `_posts` 或推到公开分支/PR。
- 告知草稿绝对路径及待确认事项，等待用户审核。素材或草稿含隐私时先脱敏；忽略规则并非加密或访问控制。

## 文章格式

现有站点为 GitHub Pages 原生 Jekyll，网页后台为 Sveltia CMS。发布文件为 `_posts/YYYY-MM-DD-short-slug.md`，UTF-8。新文章 front matter：

```yaml
---
title: "用户确认的标题"
date: "YYYY-MM-DD"
description: "一句话摘要"
category: 笔记
tags: [学习]
---
```

- 将日期占位值换成真实有效日期，按站点时区 `Asia/Shanghai`，文件名前缀与 date 一致。用户指定历史日期可保留；未来日期不保证定时发布，需要后续构建，不擅自承诺定时上线。
- 分类当前为 `笔记`、`踩坑`、`随想`、`生活记录`；标签为可选字符串列表。标题和摘要正确 YAML 转义；正文从二级标题开始即可，布局会展示文章标题。
- 新文章 slug 宜用简短稳定的小写英文和连字符；已有文章不要随意改文件名或日期，以免破坏链接。检查同名文件，禁止静默覆盖。
- 图片放在 `assets/uploads/` 并用站内路径引用，只添加用户允许公开的素材，检查截图中的账号、密钥与私人信息。
- Jekyll 会处理 Markdown 内的 Liquid；包含 Liquid 模板示例时使用合适的 raw 包裹，并核对渲染。不要假设代码围栏一定阻止模板执行。

## 发布模式（用户明确要求时）

1. 确认用户要发布的具体稿件/版本及目标仓库；“可以”仅继承明确的上一项提议，不扩大为以后所有文章的发布授权。未确认的新内容留作草稿。
2. 发布前检查标题、摘要、有效日期、分类、YAML 类型、非空正文、图片链接、隐私和未替换占位内容。核对 Git 状态与远端最新状态；有不相关改动或分叉时保护原改动，不强推、不自动覆盖冲突。
3. 只将获准的稿件与附件加入 `_posts` / `assets/uploads`，逐项暂存并审查 diff；不要 `git add .`，不夹带规则、配置或其他 Agent 的文章。检查暂存区若有用户已有内容，不混入本次提交。
4. 通过现有认证提交、推送获准的分支（当前发布分支 `main`）。不要修改全局 Git 身份设置；若需身份，优先沿用仓库设置，或使用此仓库既有的公开身份 `YoungShip <YoungShip@users.noreply.github.com>` 作单次命令配置。
5. 查看对应提交的 GitHub Pages 构建状态，并打开最终文章链接核对标题/正文。若构建失败、超时或访问失败，报告提交和真实状态；不要把“push 成功”等同于“已上线”，也不要重复推送相同稿件试运气。无需为此迁移托管或添加新部署服务。

网页后台的“保存”同样属于公开提交，不是私人草稿按钮。可以用 Git 发布而不操作网页；没有工具访问时交稿，不要求用户将令牌发到聊天。

## 交付

只写稿时：给出草稿链接、简短摘要及需用户确认的事实，明确尚未发布。
发布后：给出文章 URL、提交标识和实测部署状态。修改范围限稿件与必要附件，未另获授权不改首页、主题、后台权限或已有文章。
