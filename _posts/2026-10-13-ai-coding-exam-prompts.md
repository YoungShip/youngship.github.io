秋招笔试开始出现 AI Coding 题：给一个多文件的预设工程和一份很长的需求文档，在 90 分钟左右把一个服务实现完整，全程可以用平台内置的 AI 助手。携程 2027 届秋招的研发类笔试就新增了这个模块（[来源](https://campus.niuqizp.com/job-vlk5a5naz.html)）。

下面是我整理的做法和提示词。

## 先弄清楚怎么评分

- **两部分得分**：隐藏测试用例 + 和 AI 的对话过程。对话记录会随代码一起提交。
- **提交后有分类反馈**：会告诉你各类用例通过几条，以及失败类型的提示。
- **提交有次数限制，取最高分**：改坏了不扣分，只要能回退。
- **启动要求必须照做**：端口、启动命令、返回格式错一处，全部用例都会失败。
- **AI 能改文件，但不能跑终端**：测试要自己点运行，再把结果贴给它。
- **有的公司还限制对话轮数**：开考先看清配置里的模型、提交次数和轮数上限，轮数紧就更不能浪费在「再改改」上。

过程分不低。牛客的 AI Coding 考核按「过程 + 结果」联合评估，维度包括提示词设计、工具调用、任务拆解与交付（[来源](https://m.tech.china.com/redian/2026/0718/072026_1920548.html)）。有面经称测试用例约占 0.4、过程约占 0.6，这是个人经验，没法核实（[来源](https://post.smzdm.com/p/ak8lnoq4/)）。

判分看的是：你在做决定，AI 在执行。HelloInterview 访谈面试官后总结为四点：拆解问题、掌控 AI、验证产出、沟通清晰（[来源](https://www.hellointerview.com/learn/ai-coding/overview/introduction)）。

## 核心原则

把 AI 当成一个手很快、偶尔会错的同事：我定方向和范围，它写代码。

1. **先理解，后写代码**。第一条消息让 AI 总结需求，不是直接写。
2. **一次只做一件事**。一轮只处理一类问题，范围越小越不容易改坏已通过的部分。
3. **先说要改什么，再动手**。让 AI 先说明改哪个文件、哪个函数、会不会影响别的逻辑。
4. **用原文对照**。让 AI 引用 README 原文规则来检查代码，比凭印象猜准得多。
5. **用分数做判断**。看不懂代码也没关系：分数涨了就保留，降了就回退。
6. **信息给完整**。贴完整的报错和失败提示，不要只说「不对」「再改改」。
7. **只认运行结果**。AI 说「应该能过」「测试通过」都不算，以自己跑出来的结果为准。也不许它为了变绿删测试、吞异常。

提示词越简单越好：一句话说清目标，列出约束，说明要什么样的输出。下面的模板是骨架，用的时候换成自己的话、带上题目里的具体名词。原样套模板、假装协作，过程记录里看得出来（[来源](https://www.mianlingai.com/blog/nowcoder-ai-coding-exam-guide-2026/)）。

## 解题流程与提示词模板

动手前先不改任何代码，直接跑一次样例，看看预设代码原本的状态。这样后面出错时能分清是题目本来就有的问题，还是自己改出来的。

然后按顺序发这六条，`@` 的部分换成实际文件名。

**1. 理解题目（不写代码）**

```text
@README.md @sample_testcases
先不要写代码。请帮我：
1. 用几句话总结这道题要实现什么
2. 列出「服务启动要求」的所有硬性规定，以及哪些文件不能改
3. 列出所有接口：路径、方法、参数、返回格式、错误码
4. 把需求整理成验收清单，每条写清怎么验证
5. 列出容易出错的边界情况（幂等、并发、空值、上限）和文档里的模糊点，
   文档有冲突的地方指出来，不要自己选
```

**2. 定方案**

```text
按上面的理解，给我一个实现方案：用什么数据结构存状态、
每个接口的处理逻辑、重复请求怎么处理。方案确认后再写代码。
```

**3. 写代码（在预设结构上补全）**

```text
请在现有预设代码结构上实现，不要推翻重写：@main.py @src/...
要求：
- 先说明每个文件的作用和需要补全的地方
- 严格遵守启动要求：（粘贴第 1 步列出的几条）
- 返回字段名、状态码、错误码与 README 完全一致
- 改完后列出改了哪些文件、每个文件改了什么
```

**4. 跑样例，反馈结果**

```text
运行了测试，结果如下：（粘贴完整输出）
先不要改。请列出最多 3 个可能的根本原因，
说明怎么确认是哪一个，再做最小的修改，只改相关的文件。
```

**5. 样例通过后立刻提交，按类修复**

```text
提交得分 XX，以下是「审计链」类的失败提示：（只贴这一类）
先不要改代码。请引用 README 中相关的原文规则，
说明当前代码哪里不一致，打算改哪个文件的哪个函数，
会不会影响已经通过的逻辑。
```

**6. 确认后再改**

```text
可以，只修改和这一类直接相关的代码，其他部分不要动。
```

先修哪一类：失败条数多的、规则写得死的（格式、顺序、哈希）、属于「通用类型」的。改一处能救一片。

最容易踩的坑是一次把所有失败都丢给 AI。它会去动共用的底层逻辑，结果一批原本通过的用例一起挂掉。所以第 5、6 步一定要一类一类来。

## 卡住了怎么办

| 情况 | 怎么做 |
| --- | --- |
| 分数涨了，还有失败 | 保留这版，告诉 AI「上次修改有效，不要改动已生效的部分」，继续修下一类 |
| 分数没变，失败提示变了 | 原问题解决了，暴露了下一层，把新旧提示都贴给它 |
| 分数没变，提示完全一样 | 告诉它「上次判断不对」，要求引用原文、换一种修复思路 |
| 分数下降 | 从「时间线」回退到高分版本，告诉 AI 那次改动导致回退，换一种只影响这一类的改法 |
| 连续两三轮没进展 | 新开对话，带上 README、当前代码、失败提示和已尝试过的方向 |
| 同一类卡了三四轮 | 先放下，去修别的类，分数按用例算 |

分数没变时：

```text
按你的修改提交后，得分还是 XX，失败提示完全没变：（粘贴）
说明上次的分析不对。请：
1. 针对每个失败用例，引用 README 里对应的原文规则
2. 说明当前代码的实际行为，和规则差在哪里
3. 给出和上次不同的修复思路，不要改动其他已通过的部分
```

新开对话时：

```text
@README.md @当前代码文件
已通过 XX 个用例，以下用例反复修改都失败：（粘贴）
之前尝试过：（改过的方向）
请重新分析根本原因。
```

## 对话分：几句通用追问

对话分看的是在思考和推动，不是转发。下面几句看不懂题目也能用，还能帮 AI 找出漏掉的情况：

- 理解题目后：「这些边界情况按优先级排一下，哪些最可能被测试到？」
- 定方案后：「这个方案有什么缺点？有没有更简单的做法？」
- 测试失败时：「你确定是这个原因吗？还有没有其他可能？」
- 全部通过后：「再对照文档逐条检查一遍，有没有遗漏的规则？」

要避免的是「帮我写」「还是不对」「再改改」这种没信息量的来回，以及 AI 说什么就照单全收。

## 时间分配

按 90 分钟估：

| 阶段 | 时间 |
| --- | --- |
| 读启动要求、理解题目、定方案 | 10–15 分钟 |
| 写代码、跑通样例 | 25–30 分钟 |
| 提交、按类修复 | 35–40 分钟 |
| 收尾：停止大改，确认最终版能跑 | 最后 10–15 分钟 |

时间不够时，先保证主链路能跑、能过冒烟用例，边角功能放到最后。
