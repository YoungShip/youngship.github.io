这次原本只是想让 Codex 打开 Google，搜点东西，结果先被浏览器连接问题卡住了。

当时的困扰是：好像只有打开代理软件的虚拟网卡，也就是 TUN 模式，浏览器工具才能正常工作。我不想为了这一个功能一直开着 TUN，于是和 Codex 一起排查了一遍。

最后恢复到了我想要的状态：**Clash 保持运行、系统代理开启，TUN 关闭，Codex 仍然能操作内置浏览器完成搜索。**

先说清适用范围：这是 2026 年 9 月 20 日在我这台 Windows 电脑上的一次修复记录。用到的是当前运行时的本地补丁，不是官方通用修复，也不代表所有浏览器超时都是同一个原因。

## 症状不只是“网页打不开”

最初的问题并不是每次都完全失败。旧的浏览器工具曾经成功读到过页面，但多次操作会卡到 30～60 秒后超时。

这就容易让人分不清：是 Google 访问不了，还是代理节点不稳定，或者是 Codex 根本没连上浏览器？

当时确认的环境是：

- Windows 上运行 Codex 桌面应用。
- Clash 的系统代理已开启，本地代理端口为 `127.0.0.1:7890`。
- 排查时 TUN 已关闭。
- 不开 TUN，通过普通 HTTP 代理仍然可以访问 Google。

最后一条很关键：它说明不用 TUN 也有一条可用的访问路径，但还不能证明浏览器工具实际用上了这条路径。

## 真正的线索：主程序有代理，子进程却没有

排查继续往下看的是进程环境，而不只是代理软件界面上的开关。

当时的检查结果如下：

| 检查对象 | 代理相关环境变量 |
| --- | --- |
| Codex 主程序 | 存在 |
| 主 app-server 进程 | 存在 |
| 浏览器工具的 Node 启动进程 | 缺失 |
| 浏览器工具的 node_repl 子进程 | 缺失 |

这里检查的变量是 `HTTP_PROXY`、`HTTPS_PROXY`、`NO_PROXY` 和 `NODE_USE_ENV_PROXY`。

也就是说，**“Codex 主程序知道代理在哪里”，不等于“它启动的每一个工具进程也知道”。**

进一步检查发现，桌面应用生成的浏览器工具配置只放行了 `CODEX_WINDOWS_REGISTERED_CORE`，而且会重写这份配置。代理环境变量没有被保留下来，直接改生成的配置也不是稳定的解决办法。

OpenAI 的[配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)中，`mcp_servers.<id>.env_vars` 就用于为 MCP stdio 服务额外放行环境变量。这能帮助理解问题发生在哪一层，但文档本身并不证明某个桌面版本一定存在这个问题；这次的判断来自实际进程检查。

为什么开 TUN 可能缓解？我的理解是：如果相关流量已经被 TUN 的路由规则接管，工具进程即使没拿到 HTTP 代理变量，也可能访问成功。这是对现象的解释，不是“所有 TUN 配置都能兜底”的保证。

## 这次具体改了什么

这次没有改 Clash 的配置，也没有打开 TUN，更没有关闭证书校验或扩大浏览器权限。

实际修改在浏览器工具的启动入口：`@oai/cua-repl/bin/cua-repl.mjs`。

做法是先备份原文件，再新增同目录模块 `windows-system-proxy.mjs`，并在启动入口加载浏览器工具之前加入：

```js
import "./windows-system-proxy.mjs";
```

注意，这一行本身不是完整补丁，必须有对应模块；不要直接复制到自己的安装目录里当作修复命令。

新增模块承担的事情很集中：

1. 只在 Windows 上运行。
2. 优先保留已有的 HTTP、HTTPS 代理变量；缺少时读取当前用户已启用的 Windows 系统代理。
3. 为当前工具进程补齐代理变量，让后续启动的子进程能继承。
4. 如果没有现成的 `NO_PROXY`，补上 `localhost,127.0.0.1,::1`，为本地通信保留直连；如果已有值，则保留原值。
5. 在有代理且未设置 `NODE_USE_ENV_PROXY` 时，将其设为 `1`。这依赖当时实际使用的 Node 运行时支持，不能假设所有 Node 版本都一样。
6. 系统代理配置读取失败时，不让这个辅助模块阻止工具正常启动。

读取的是 Windows 当前用户的系统代理配置，不是去获取账户密码或浏览器登录信息。

这里还有一个容易误会的地方：**应用内部的工具环境、命令行沙箱的联网配置，以及浏览器实际访问，是不同层面。** OpenAI 的[安全与网络说明](https://learn.chatgpt.com/docs/agent-approvals-security#traffic-outside-the-command-network-proxy)也区分了命令网络代理和浏览器、Computer Use 等流量。因此，不能简单把“命令行可以联网”当成“浏览器工具也一定正常”。

## 改完不能只看“启动成功”

这次验证分成了两步。

先检查启动链路：刻意移除代理变量，用真实的浏览器工具启动命令启动一个独立验证进程。结果是 MCP 初始化成功，新启动的 `node_repl` 进程也拿到了预期变量：

```text
HTTP_PROXY=http://127.0.0.1:7890
HTTPS_PROXY=http://127.0.0.1:7890
NO_PROXY=localhost,127.0.0.1,::1
NODE_USE_ENV_PROXY=1
```

这里的端口是这次环境中的值，不是所有人的默认配置。

随后，我完整重启了 Codex，再让它执行最初真正想做的操作：

1. 读取内置浏览器里的 Google 首页。
2. 输入“OpenAI 官方网站”。
3. 提交搜索。
4. 读取结果中的标题和摘要。

这些步骤都成功了，搜索结果中能读到 OpenAI、ChatGPT 等内容。当轮页面读取和搜索操作的单次工具调用在 1 秒内返回，没有复现之前的长时间超时。这里说的是工具调用返回时间，不是严格测量的网页完整加载耗时。

更重要的是，测试前后都确认了 `tun.enable=false`，Clash 保持 `rule` 模式，测试期间没有再调网络设置。这样才算验证了“不依赖开启 TUN”这个目标，而不只是碰巧打开了一次网页。

## 这个修复也有边界

恢复使用不等于问题从此永久消失。

这次补丁修改的是应用自带运行时文件，应用更新如果替换了运行时，补丁就可能失效。届时需要重新检查现象和代理变量，不能盲目把旧文件覆盖到新版本上。如果官方已经修复，应优先使用官方版本。

它也不是完整的系统代理兼容层。这次验证的是当前启用的静态系统代理；PAC 自动代理脚本、企业认证代理或其他复杂网络环境，不在这次测试结论里。

原始入口文件有备份。如果要撤销，恢复与该运行时版本匹配的原始启动文件，再重启 Codex即可；新增模块没有被导入后就不会执行。不要用不匹配版本的备份回滚。

现在的使用方式是保留 Clash 和系统代理，TUN 可以关闭。这不意味着直连网络突然可用了，也不保证所有网站、所有节点都不再超时。

## 留给下次排查的提醒

这次最值得记住的，并不是某个端口或者那一行 `import`，而是一个排查顺序：

**确认访问路径可用，再确认真正执行任务的进程拿到了正确配置，最后用实际操作验证。**

主程序能联网，不代表工具进程能联网；浏览器里已经有页面，不代表 Agent 能继续读写；一次工具初始化成功，也不代表整个搜索过程能走完。

下次再遇到“只有开 TUN 才能用”，我会先沿着这些层次去看，而不是直接把“必须开虚拟网卡”当成结论。
